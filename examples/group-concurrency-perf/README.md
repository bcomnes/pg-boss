# groupConcurrency fetch benchmark

This benchmark preserves the three PostgreSQL query shapes evaluated while fixing
[#842](https://github.com/timgit/pg-boss/issues/842):

1. The original materialized active-count CTE joined before and after `LIMIT`.
2. The intermediate saturated-group `ARRAY()` InitPlan and post-`LIMIT` count join.
3. The current query generated by `plans.fetchNextJob()`.

It provisions an isolated real pg-boss schema for every measurement, seeds current or deliberately
stale statistics, executes the complete claim `UPDATE` under `EXPLAIN ANALYZE`, checks the claimed
row count, prints execution and plan-loop summaries, and drops the schema afterward.

Run one pass over the core scenarios:

```sh
npx tsx examples/group-concurrency-perf/index.ts
```

Reproduce the five-run median comparison:

```sh
RUNS=5 npx tsx examples/group-concurrency-perf/index.ts
```

Run the slower 10,000- and 50,000-active-group probes:

```sh
MODE=large npx tsx examples/group-concurrency-perf/index.ts
```

Select specific scenarios or retain fixtures for manual inspection:

```sh
SCENARIOS=incident_stale,batch_1000 RUNS=1 npx tsx examples/group-concurrency-perf/index.ts
KEEP=1 SCENARIOS=incident_stale npx tsx examples/group-concurrency-perf/index.ts
```

`POSTGRES_HOST`, `POSTGRES_PORT`, and `POSTGRES_PASSWORD` use the same configuration behavior as
the integration test suite. The benchmark targets PostgreSQL because its assertions inspect
PostgreSQL-specific execution-plan nodes.

Elapsed times are observations, not pass/fail thresholds. Compare plan shape and loop counts before
comparing absolute duration across machines.
